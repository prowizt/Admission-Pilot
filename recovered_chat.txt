## 1. 마지막으로 승인된 구현 계획 (Implementation Plan)
------------------------------------------------------------
# [RAG 검색 고도화 및 출처 파일명 표기 구현 계획서 (통째 저장 유지 버전)]

사용자님의 피드백을 반영하여, 오류 유발 가능성이 큰 **"페이지 단위 청킹 복원"은 철회**하고, 안정성이 입증된 **"통째 파일 저장" 방식을 그대로 유지**합니다. 

대신, 통째 저장 상태에서도 `2027학년도 모집요강`이 누락 없이 `전문대학입학전형기본사항`과 함께 공존하여 정밀 분석될 수 있도록 RAG 로직을 다음과 같이 고도화합니다.

---

## 🛠️ Proposed Changes

### 1. 통째 저장 방식 유지 및 기존 ChromaDB 청소 상태 활용
- 페이지 청킹은 적용하지 않고 문서 통째 저장(단일 청크) 상태를 유지합니다. (ChromaDB `rule_db`는 이미 깨끗이 청소된 8개의 통째 문서 상태로 바로 운용 가능)
- 페이지 번호는 출력에서 제외하되, 메타데이터에 살아있는 **출처 파일명/문서 제목(예: `2027학년도 모집요강`, `2027학년도 전문대학입학전형기본사항`)은 답변에 명확히 표기**하도록 유도합니다.

### 2. RAG 검색 범위 (`n_results`) 확장 및 쿼리 정제 (`backend/main.py`)
- **검색 청크 수 상향:** `rule_db`에서 조회하는 상위 문서 개수(`n_results`)를 **기존 2에서 5로 상향**합니다. 
  - 통째 저장 방식에서는 문서 1개당 청크가 1개이므로, `n_results=5`로 늘려주면 2027학년도와 관련된 모든 규정 문서(모집요강, 기본사항, 학사내규 등)가 유사도 랭킹 경쟁에서 스킵되지 않고 **100% LLM 컨텍스트에 한 번에 다 들어갑니다.**
- **임베딩 쿼리 텍스트 정제:** 쿼리 조회 시 `scraped_context` (CSV 원문 텍스트)를 쿼리에 합치던 로직을 제거하고, **순수 자연어 질문(`rag_query`)만 쿼리로 사용**하여 의미 기반 매칭 스코어를 최적화합니다.
  - 첨부파일인 CSV 텍스트는 RAG 검색 용도에서만 제외될 뿐, LLM 추론 영역(`<검토 대상 문서>`)에는 정상 주입되어 수치 대조에 정상 활용됩니다.

### 3. 출처 표기 강화 및 프롬프트 가이드 (`backend/main.py`)
- RAG 텍스트 컨텍스트 앞에 **`◆ [출처 문서: {title}]`** (페이지 생략) 헤더를 강제 부착합니다.
- 최종 답변을 생성하는 시스템 프롬프트에 **"지적한 모든 위반 우려 및 행정 헛점 사항에 대해, 반드시 근거가 되는 구체적인 규정 문서의 제목(예: 2027학년도 모집요강, 전문대학입학전형기본사항 등)을 괄호 형태로 명시할 것"**을 명문화합니다.

### 1. 페이지 단위 청킹(Page-by-Page Chunking)과 이전 방식의 본질적인 메커니즘 차이

사용자님께서 제기해주신 의문은 매우 날카로우며, 실제로 RAG(Retrieval-Augmented Generation) 시스템 설계에서 가장 빈번하게 발생하는 **검색 누락(Retrieval Failure)** 현상과 맞닿아 있습니다. 이전 방식과 현재 방식의 핵심 차이는 다음과 같습니다.

| 구분 | 이전 방식 (파일 통째 저장) | 현재 방식 (페이지 단위 청킹) |
| :--- | :--- | :--- |
| **저장 형태** | PDF 문서 전체 텍스트를 하나의 커다란 청크(chunk)로 DB에 통째로 저장 | PDF 문서를 각 페이지별로 잘라 53개의 별도 청크로 쪼개어 저장 |
| **검색 메커니즘** | ChromaDB에서 해당 문서를 딱 1개만 매칭해서 가져와도, **1페이지부터 53페이지까지의 모든 텍스트**가 LLM 컨텍스트에 한 번에 주입됨. | 질문과 연관성이 높은 상위 N개의 **특정 페이지들**만 선별하여 LLM 컨텍스트에 주입됨. |
| **장점** | 한글 유사도 검색 성능이 완벽하지 않더라도 **문서 전체 맥락이 유지**되므로 수치 비교 시 정보 누락이 전혀 없음. | 불필요한 페이지를 배제하므로 토큰 사용량과 API 비용이 크게 감소하고 속도가 빠름. |
| **단점** | 문서 크기가 커지면 LLM의 프롬프트 허용 토큰 한계를 초과하여 에러가 발생할 수 있고, 불필요한 텍스트로 인해 노이즈가 생김. | **질문 및 첨부파일과 유사도 매칭이 어긋날 경우, 정작 중요한 페이지가 탈락하는 검색 누락(Retrieval Gap)이 발생함.** |
